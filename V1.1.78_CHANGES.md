# v1.1.74 — Ult drags to his right side + Arlott described in all five locales

## 1. Final Slash now drags instead of pushing (owner: "1 side drag")

Canon, two independent sources:
- gamingonphone (2022-12): "directing all of his enemies to his **right side**"
- TV Tropes: "dragging them to the **side edge** of the area of effect, the
  direction where he swung his lance to"

v1.1.73 pushed every target radially away from Arlott, so where a target landed
depended on where it happened to stand. That is now a rotation: take the cast's
`Direction` aim, turn it -90 degrees, and drop **every** target at
`ULT_DRAG_DISTANCE` (30,000) from Arlott on that side.

| | v1.1.73 | v1.1.74 |
|---|---|---|
| displacement | radial, away from caster | **-90 deg from the swing aim** |
| landing | one per target, depends on its start | **one shared point per cast** |
| stacks targets? | no | **yes** — so ult -> Vengeance hits the pile |

The shared landing point is the point of the change: canon players use the ult to
put a group in one spot, then Vengeance the stack.

Aim selection: `InputTargetV1::dir_*` when the host sends a `Direction` (the
ult's `casting_type`), else the caster->target line, else +x. Never degenerate.

**Not verified in-engine.** Which screen side counts as "his right" depends on
the engine's coordinate handedness, which no file states.

All five now carry attack, passive, skill1, skill2, ult, plus the four skill
names. Translations follow the file's existing conventions (colour tags, number

## 3. S2 CC immunity is now documented

The mechanic shipped in v1.1.72 (`mlbb_heroes:arlott_s2_cc_immune`, 12 ticks of
CC immunity covering the 8.57-tick max-range dash) but the description never
mentioned it. Every locale now states it: "cannot be interrupted while dashing".

# v1.1.75 — the v1.1.74 SOURCE ARCHIVE WAS BROKEN. Rebuilt.

## What was wrong with the v1.1.74 archive
`sdk/candidate/lib.rs` had **no `mod arlott;` and no `arlott::register(...)`**.
Compiled as shipped, the archive produced a mod **with Arlott completely absent** —
correct DLL, correct assets, no hero. Every test still passed, because every test
lives inside `arlott.rs`, a file the crate root was free to ignore. A native
effect that is never registered is dead code that compiles.

The archive was also half the usual size (25 MB vs 46 MB) because the wrapper that
built it packaged the runtime tree plus `src/` + `sdk/` only. v17 and earlier
carried the whole dev tree: raw source art (`source/`, 24.5 MB), `tools/`,
`docs/`, `patches/`, `reports/`, build scripts, `Cargo.lock`.

The owner caught it from the file size alone.

## Fixes in v1.1.75
1. **Wiring restored and made authoritative.** `sdk/candidate/lib.rs` is now the
   real crate root from the build tree, with `mod arlott;` (line 8) and
   `arlott::register(&mut module);` (line 2396). `lib.rs` is now kept in the
   workspace at `arlott_work/src/lib.rs` so it can never go missing again.
2. **Dev tree restored**: `source/` (raw MLBB art scraped from the wiki),
   `tools/`, `docs/`, `patches/`, `reports/`, `build.sh`, `build.ps1`,
   `Cargo.lock` — archive is now **881 files / 55 MB** like the ones before it.
3. **New checker: `alpha_work/check_source_archive.py`.** Validates an archive
   from the outside: crate root declares and registers the hero, hero module and
   champion data present, every `mod X;` has a file, payload volumes populated,
   and this is a source archive rather than a renamed runtime. Run against the
   v1.1.74 zip it reports exactly the defect above; against v17 it correctly
   reports "arcade has no arlott" because v17 predates him.

## Honest note on the test added
`arlott_is_actually_wired_into_the_crate_root` was added to `arlott.rs`, and it
**cannot catch this failure** — if `mod arlott;` is deleted the module is not
compiled, so the test is not compiled either. It passed 111/111 on the broken
tree. It is kept because it catches the *half*-failure (module declared but never
registered), which is the likelier accident. The real guard is the python checker,
which reads the archive as a zip rather than trusting the build.

## Unchanged from v1.1.74
Ult right-side drag, five-locale champion text, S2 dash CC immunity line.
Tests **111/111**. DLL 2,255,233 B.

# v1.1.76 — Arlott S1 points the right way; Alpha's true damage cut

## 1. Arlott S1 drew a sideways crescent (reported from gameplay)

"why is his skill 1 effect sides wards instead of downward slash or slam"

**The wiring was already correct.** `skill1` is `casting_type: Direction`, the
damage is a `LineRangeProjectile`, and the sprite row `skill` already animates a
proper downward slam (frames 4-5 drive the lance into the ground). The problem was
the **art**: `arlott_s1_wave#sheet.png` was a single horizontal crescent that filled
the whole 96 px cell in *every one of its 6 frames* (art ran x=0..95 in all six).
Whichever way the engine aimed it, what reached the screen was a slash lying across
the ground — a sideways sweep.

**Fix:** the wave is rebuilt from the original artwork so the palette, pixel density
and hot-white leading edge are unchanged, but each frame is the same art squeezed to
a finite width and its leading lip walks forward across the animation:

| frame | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| ink x-range | 11-33 | 14-43 | 17-53 | 20-61 | 22-67 | 30-78 |

It now starts at his feet, travels to roughly 80% of the cell, and never touches
both edges. The tail is alpha-faded so the direction of travel reads. Vertical
squash to 86% keeps it hugging the ground like a shockwave rather than a slash.

Cell size (96x48), frame count (6), `anchor_x/y` (0.5 / 1.0) and the `.fanim` binding
are all untouched — this is an art-only change, no data edits.

`tools/build_s1_wave.py` regenerates the sheet and writes
`effects/arlott_s1_wave#geometry.json`, which the new guard test reads.

## 2. Alpha nerf: Lock-On laser and proc rate

Post-match bar: **17,759 of 25,920 damage = 69% True**. The lock-on laser is
`DamageTypeV1::Fixed`, so no armour applies to it, and it charged on **every second**
landed hit — and Alpha lands a lot of hits (basic attacks, S1/S2 strafes, all five
ult strafes).

| | before | after |
|---|---|---|
| laser per hit | 45 + 4/level + 25% AD | **30 + 3/level + 15% AD** |
| hits to charge | 2 | **3** |
| L11 vs 110 AD | ~112 | **~76** |

Both levers were used deliberately: the per-hit cut moves the number, the proc-rate
change moves the *share*. A damage-only nerf leaves him reading as a true-damage
hero because the frequency is unchanged.

Untouched: S1/S2 strafe damage, ult strafe damage, the 30% slow on laser hit.

# v1.1.78 — S1 draws where it hits; Arlott's numbers come up

Two things in one release: the effect you reported, and the damage question you
asked after two scoreboards.

## 1. "why does the effect of skill 1 appear on him, not in front of him?"

It was **never the art**. The data told the engine to draw both effects on the caster:

```
"skill": { "effect": { "effects": [
    CasterAnimation      skill
    CasterViewEffect     arlott_s1_wave    <-- the fissure, at the CASTER
    LineRangeProjectile  arlott_s1_slam
    CasterViewEffect     arlott_s1_far     <-- the burst, at the CASTER
]}}
```

`CasterViewEffect` means "play this at the caster", and both were bound in
`view_effects` with `"is_follow": false` — "spawn where you were and stay put". So the
fissure and the starburst both sat on Arlott. Alpha's S1 has no `CasterViewEffect` at all;
it draws its beam from the `view_projectiles` binding, which is why it lands out front.

**Fix:** both `CasterViewEffect`s deleted. The fissure now comes solely from
`view_projectiles → arlott_s1_slam`, and the impact burst still fires from the
`mlbb_arlott_s1_stun` view_buff — i.e. **on whoever gets stunned**, at the far end,
which is where canon puts the longer stun.

**Art consequence.** A projectile sprite cannot be a "reveal". v1.1.77's crack opened
left-to-right from his feet, which would have carried a growing-from-the-left-edge
animation down the field with it. Rebuilt as a **constant-length** fissure: the same
92 px crack in all six frames, with only the light animating (white-hot core pulses,
far-end flare peaks on f2, settles by f5). Squash 0.90, margin 2 px, and the `.fanim`
anchor moved from `0.5 / 1.0` to **`0.5 / 0.5`** so it centres on the projectile the way
Alpha's beam does.

## 2. Damage: +30%, not the +45% first proposed

Two scoreboards, both 1/0/10, both zero True damage:

| | game 1 | game 2 |
|---|---|---|
| length | 11:00 | 13:37 |
| damage | 6,775 | 10,908 |
| per minute | 616 | 801 |
| CS | 69 | 80 |
| split | 98 / 2 / 0 | 97 / 3 / 0 |

The second game tracked farm, not a defect. What *is* out of family is his scaling:

20%. So:

| slot | was | now |
|---|---|---|
| S1 | 90 + 25% AD | **100 + 35% AD** |
| S2 | 60 + 20% AD | **90 + 35% AD** |
| ult | 150 + 50% AD | unchanged (its value is the displacement) |

Applied in `champion/mlbb_arlott.data_champion` **and** in the player-facing text in all
**five locales** (en, zh-hans, zh-hant, ko, ja) — the numbers are spelled out in the
skill descriptions, so a data-only change would have made the tooltips lie.

## 3. Two new guards, both proven to fail

This defect survived a release because nothing checked it:

- **Rust** `s1_never_draws_the_fissure_on_the_caster` — fails if S1 contains any
  `CasterViewEffect`, or if the `view_projectiles` binding is lost.
- **Rust** `s1_fissure_is_a_projectile_sprite_and_holds_its_length` — the sheet must be
  the same length in every frame and declare `mode: projectile_static`.
- **Python** `validate_data_champion.py` — resolves `CasterViewEffect` names and
  `view_projectiles` bindings through `view_effects` and fails if they draw the **same
  anim asset**. Comparing names was not enough: the caster effects were `arlott_s1_wave`
  / `arlott_s1_far` while the projectile was `arlott_s1_slam`, so the names never
  collided — only the underlying sheet did. It also fails a `LineRangeProjectile` with no
  `view_projectiles` binding (damage that fires invisibly).

Both were run against a reconstructed v1.1.77 data file and both failed on it; both pass
on the shipped one.
